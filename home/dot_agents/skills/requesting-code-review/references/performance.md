# Performance lane — 检查要点

## 重复工作

- 循环体内是否有可提取到循环外的重复计算
- 重复解析同一数据（JSON、正则、模板）是否可缓存
- 同一请求中对相同资源的重复查询是否可合并

## 复杂度退化

- 是否引入 O(n²) 或更差的嵌套循环
- 排序、查找是否使用了合适的数据结构（map vs 线性扫描）
- 递归是否有尾调用或记忆化机会

## 过度分配

- 热点路径中是否有不必要的大对象或临时对象创建
- 字符串拼接是否用了低效方式（循环 `+` 而非 Builder/Join）
- 大 slice/map 是否预分配了合理容量

## I/O 与网络放大

- 是否存在 N+1 查询（循环中逐条请求数据库或 RPC）
- 批量操作是否可以合并为单次调用
- 响应体是否可以流式处理而非全量加载到内存

## 缓存与批量机会

- 高频只读数据是否有缓存层，TTL 是否合理
- 外部调用结果是否在请求生命周期内复用
- 批量写入是否比逐条写入更合适

## 热点路径锁粒度

- 是否有可以缩小的临界区
- 读多写少场景是否可改用 RWMutex 或无锁结构
- 是否有不必要的全局锁

## 判断原则

- 只在存在明确性能影响或已知热点路径上报告问题
- 非热点路径的"理论上可以优化"不写入 findings
- 优化建议应具体（指出位置和方案），不泛泛而谈
