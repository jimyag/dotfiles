# Architecture lane — 检查要点

## 目录

- 判断原则
- 分层、依赖方向和抽象必要性
- 模块深度、边界和职责
- 核心链路、错误体系和容错
- 可扩展性、维护性和架构性风险
- 全仓库架构审查
- 输出要求

## 判断原则

- KISS：能用直接结构解决的问题，不引入额外层、接口、框架或模式。
- SOLID：职责单一、依赖方向稳定，扩展点服务真实变化，而不是提前制造抽象。
- DRY：消除真实重复，不为表面相似强行合并不同语义。
- 高内聚低耦合：核心业务、基础设施、展示层、存储层和外部集成边界清晰。
- 所有结论必须有文件、行号或相邻调用链证据；没有证据的判断放入待确认，不输出为确定问题。

## 分层与依赖方向

- API/handler/controller、业务服务、领域逻辑、数据访问、基础设施、UI/CLI/TUI 等层级是否职责清楚。
- 是否存在上层细节泄漏到下层，例如业务规则进入通用工具层、UI 状态进入 runtime、存储结构绑死业务流程。
- 是否存在反向依赖、循环依赖、跨层直连或绕过 canonical service/helper 的调用。
- 新增层级是否提供真实隔离，例如隐藏外部系统差异、稳定契约、收敛错误语义；只转发参数的层级通常不是有效架构。

## 抽象必要性与空概念

- 新增接口是否至少有一个真实实现和明确替换场景；只有一个实现且调用方不需要隔离时，优先用具体类型。
- wrapper/adapter/middleware 是否改变语义、收敛复杂度或隔离边界；只改名、只转发、只包一层日志的薄封装应作为维护风险审查。
- 是否出现空模块、空接口、空基类、空 service、占位 manager、无业务规则的 domain 层等"为了分层而分层"的结构。
- 设计模式是否解决实际问题；如果引入 factory、registry、strategy、event bus、plugin layer 后调用链更难追踪，必须指出收益是否抵得上复杂度。
- 是否把未来可能性当作当前抽象理由；没有明确变化轴、调用方或兼容需求时，不接受提前抽象。

## 模块深度与测试表面

- 对疑似薄抽象执行删除测试：假设删除该模块、接口或 wrapper，复杂度是直接消失，还是被迫扩散到多个调用方。前者说明它可能只是转发层，后者说明它确实在集中复杂度。
- 接口不只包含类型签名，还包含调用方必须理解的顺序、不变量、错误语义、配置和性能约束；评估模块是否用较小且稳定的接口隐藏了足够多的实现复杂度。
- 调用方和行为测试应尽量通过同一稳定接口验证结果；如果测试必须穿透多层内部细节才能证明核心行为，检查接口位置、职责或可观察结果是否设计错误。
- 只有存在真实变化轴时才引入 seam/adapter，例如生产实现与可运行的测试替身、两个真实后端或明确兼容边界。一个实现加一个为 mock 而造的空接口，通常不足以证明抽象有价值。
- 深化模块不是机械合并文件或删除所有内部接口；生命周期、权限、事务、部署和外部系统边界仍需保持显式，内部可替换点不必全部暴露给调用方。

## 模块边界与职责

- 模块名、公开 API、内部数据结构是否表达同一个概念，避免一个模块同时承担编排、状态、I/O、展示和错误翻译。
- 核心业务逻辑是否与日志、指标、配置、重试、缓存、序列化、HTTP/CLI/TUI 等基础设施解耦。
- 通用工具是否真通用；如果工具层开始包含业务分支、产品术语或环境假设，应回收到拥有该概念的模块。
- 是否新增重复 helper、近似类型或平行实现，导致后续修改必须同步多处。
- 是否有上帝模块、面条式编排、过长文件或函数膨胀，把多个生命周期混在一起。

## 核心链路清晰度

- 从入口到核心处理再到输出/持久化的主链路是否能顺序追踪。
- 状态所有权是否明确：谁创建、谁修改、谁释放、谁负责并发保护。
- 会话、任务、请求、工作区、连接、事务、临时文件、锁、后台 goroutine/thread 等生命周期是否闭环。
- 编排逻辑是否散落在多个中间层、回调、全局变量或隐式 side effect 中，导致失败路径难以推理。
- 新增异步、队列、事件、缓存、重试或后台任务时，是否有取消、超时、幂等、去重和可观测性设计。

## 错误体系与容错

- 各层错误边界是否明确：内部诊断信息保留，对外错误受控、稳定、可消费。
- 是否吞错误、静默 fallback、用默认值掩盖不变量破坏，或把所有错误压平成同一个提示。
- 错误包装是否保留 cause、资源 id、请求/会话 id、操作名等诊断线索。
- 超时、重试、熔断、降级、补偿是否基于真实失败模式；不要为普通本地调用加入复杂容错。
- 重试是否可能放大副作用；需要幂等键、事务边界或去重策略时必须指出。

## 可扩展性与可维护性

- 扩展点是否围绕真实变化轴，例如协议、存储后端、执行环境、展示层、权限模型；不要围绕抽象名词扩展。
- 新功能接入是否需要修改多个不相干模块；如果需要，说明耦合点和收敛方案。
- 配置、常量、路径、环境变量、资源限制是否硬编码到不该知道它们的层。
- 命名是否能帮助维护者定位 canonical owner；避免 manager、handler、service 等泛名掩盖职责。
- 注释是否解释约束和不变量，而不是替代码复述流程。

## 性能、安全与测试的架构性风险

- 架构是否引入 N+1 I/O、重复序列化、全量扫描、无界缓存、无界队列、全局锁或热点路径阻塞。
- 并发共享状态是否有清晰同步策略；资源释放是否覆盖成功、失败、取消和 panic/exception 路径。
- 权限、租户、工作区、文件系统、命令执行、网络访问和敏感信息边界是否在统一入口强制，而不是分散到调用点自觉遵守。
- 输入校验是否位于可信边界；内部模块不要重复猜测外部输入可信度。
- 架构核心约束是否有测试覆盖，例如生命周期、失败路径、并发、权限边界、迁移兼容和错误语义。

## 全仓库架构审查（仅用户明确要求时）

- 用户指定了模块、子系统或痛点时严格按该方向审查，不自动扩展成全仓库重构建议。
- 用户没有指定范围时，先结合一段有代表性的 `git log --name-only` 找出反复修改的热点，再以真实维护摩擦、缺陷历史或跨文件认知成本确认优先级；修改频率本身不是架构缺陷。
- 读取相关 ADR、设计文档和仓库约定，避免重新建议已经有意拒绝或受兼容性约束的方案；只有出现新的具体摩擦时才建议重开决策。
- 将结果输出为少量候选，标记 `强烈建议`、`值得探索` 或 `推测性`，并说明涉及文件、当前摩擦、建议方向、收益和证据。
- 全仓库审查默认只读，不创建 `CONTEXT.md`、ADR、HTML 报告或重构代码；用户选定候选后再进入 brainstorming、ADR 或实现流程。

## 输出要求

架构专项 finding 使用常规 P0/P1/P2 严重度，同时在原因中标明违反的原则，例如 KISS、SOLID、DRY、高内聚低耦合。

每条问题必须包含：

- 位置：文件与行号，必要时补调用链。
- 类型：必须修复 / 可优化点。
- 证据：当前 diff 或相邻上下文中的具体结构。
- 影响：复杂度、耦合、正确性、可维护性、性能、安全或测试风险。
- 建议：可直接执行的删除、合并、下沉、上移、重命名、收敛边界或补测试方案。
- 收益：说明整改后减少了什么复杂度、风险或维护成本。

如果执行了架构专项，需要给整体架构评分：

- 9-10：边界清楚、核心链路简单、错误和生命周期闭环、测试覆盖关键约束。
- 7-8：整体可生产，但存在局部边界、命名、测试或抽象成本问题。
- 5-6：主流程可用，但职责混杂、抽象失控、错误/生命周期/测试存在明显缺口。
- 3-4：核心链路难以维护，关键边界缺失或存在高风险耦合。
- 0-2：无法证明核心设计可运行或安全，存在严重架构阻断。

评分必须说明依据；不要因为文件多、层次多、命名像架构而加分。
