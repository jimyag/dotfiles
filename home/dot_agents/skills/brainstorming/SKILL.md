# 需求澄清与方案对比

## 目标

在正式实现前，把目标、约束和方案边界说清楚，避免直接开干后返工。

## 何时使用

- 用户需求还不清楚
- 一个问题有多种实现方式，需要比较取舍
- 改动会影响多个模块
- 需要先确认目标、范围、成功标准
- 需要先判断“值不值得做”或“该不该保留”

## 何时不要使用

- 任务已经很清楚，直接实现成本更低
- 只是小修小补或机械改动
- 用户明确要求直接动手

## 最小流程

1. 先看当前代码、文档和相关上下文
2. 先检查是否已有官方方案、框架内建能力或仓库既有模式，能复用就不要先发明新方案
3. 按“挑战隐含前提”先找出最可能导致返工的未知项
4. 用 1-3 个问题把目标和约束问清楚；能合理假设时直接说明假设并继续
5. 先判断是否需要 design doc / ADR / plan，不需要时不要制造文档流程
6. 给出 1 个推荐方案；只有取舍真的接近时再补 1 个备选
7. 说明取舍、最脆弱假设和主要风险
8. 在用户认可后，再进入实现或计划阶段

## 关注点

- 要解决的核心问题是什么
- 不做什么
- 改动影响哪些模块
- 成功标准是什么
- 有哪些约束：兼容性、时间、风险、维护成本
- 有没有必要做，或者有没有更低成本的替代方案
- 哪些选择如果错了代价高：接口、数据模型、权限边界、存储、部署、兼容性、长期依赖
- 哪些只是低成本实现细节，不值得在头脑风暴阶段展开

## 挑战隐含前提

当需求看似明确但仍可能返工时，先做一轮短促的 assumption challenge：

- 先读当前上下文：issue/PR、diff、README、AGENTS/CLAUDE、相关脚本、相邻实现和项目约定；能从上下文确认的答案不要再问用户
- 目标前提：用户真正要优化的是速度、稳定性、成本、体验、可维护性，还是交付范围
- 范围前提：哪些模块、平台、环境、用户群或旧行为必须保留
- 数据前提：数据规模、空值、历史脏数据、迁移状态、权限边界是否会改变方案
- 运行前提：本机路径、外部服务、网络、CI、凭据、定时任务、并发执行是否被默认假设
- 验证前提：什么现象算成功，什么命令、测试、截图或线上指标能证明方案成立

追问必须基于已读上下文并且可行动。不要为了“拷问”而泛泛提问；每个问题都要能改变方案、范围或验证方式。低风险问题能合理假设时，直接说明假设并继续。

## 文档路由

头脑风暴只判断是否需要 Design Doc 或 ADR，不在这里编写长文档。按 [Design Doc 与 ADR 路由](../_shared/design-record-routing.md) 判断；不满足条件时直接收敛到推荐方案或实施计划。

## 输出要求

- 问题少而准，不连发很多问题
- 方案要有取舍，不要只列选项
- 推荐要明确，不要模糊
- 复杂任务可转给 `writing-plans`
- 如果问题本质是“要不要做”，应先给判断，再给实现路径
- 高风险方案要明确 goals、non-goals、最可能推翻方案的假设
- 未决问题要写下一步：验证方式、需要确认的人或待查证据

## 评估模式

当用户问“有没有必要”“值不值得”“该不该保留/继续”时：

1. 先给结论：保留 / 放弃 / 转向
2. 再给 2-3 条基于当前约束的理由
3. 如果是转向，给出更具体的替代方向

不要把价值判断伪装成技术计划。

## 探索模式

当问题开放、用户明确希望多想几种方向，或单一路径容易过早收敛时，使用一轮轻量探索。不要对普通实现任务默认展开。

先定义 3-6 个评估标准，例如：

- 用户目标匹配度
- 实现复杂度
- 回滚成本
- 兼容性风险
- 维护成本
- 验证难度

然后从下面选择 1-2 种模式，不要全跑：

- `多候选择优`：生成 2-4 个完整候选，再选或合并。适合标题、命名、短文案、简短推荐。
- `草稿-批判-重写`：先出一个草稿，按标准批判，再重写。适合说明文、计划、PR 描述、重要回复。
- `生成-排序-细化`：生成不同策略或架构路径，按取舍排序，再细化胜出方案。适合产品、架构、迁移和方案设计。
- `拆解-求解-合成`：先找结构，再分块求解，最后合成。适合请求很宽或边界不清的分析任务。
- `工具锚定搜索`：先生成候选，再用代码、测试、文件、数据或网页验证能验证的部分。适合事实性、技术性或高风险判断。

输出时保留必要的搜索痕迹，但保持紧凑：

```text
评估标准 -> 候选路径 -> 推荐方案 -> 适用条件/风险 -> 下一步
```

不要生成很多只有措辞差别的候选；候选必须在假设、受众、风险姿态、方案策略或叙事结构上真的不同。

## 关键约束

- brainstorming 是为了减少返工，不是为了制造流程
- 不要对简单任务强制写设计文档
- 需求足够清楚时，应尽快进入实现
