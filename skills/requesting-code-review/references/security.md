# Security lane — 检查要点

## 注入

- SQL 注入：用户输入是否拼接进查询，是否使用参数化查询或 ORM
- 命令注入：外部输入是否拼接进 shell 命令或子进程调用
- 模板注入：用户数据是否传入模板引擎未经转义

## 鉴权与越权

- 受保护资源访问前是否做权限校验
- 是否存在 IDOR（直接对象引用）风险——用 ID 访问资源时是否验证归属
- 水平越权：用户 A 是否可读写用户 B 的数据
- 垂直越权：低权限用户是否可触发高权限操作

## 不安全反序列化与命令执行

- 外部来源的序列化数据（JSON、XML、Protobuf 等）是否未经校验直接反序列化
- 动态执行代码路径（eval、exec、反射实例化）是否受外部输入影响
- 文件路径是否做了路径穿越（path traversal）防御

## 密钥与敏感数据泄露

- token/password/secret 是否出现在日志、响应体、错误信息中
- 密钥是否硬编码在源码或配置文件（应使用环境变量或密钥管理服务）
- 错误信息是否泄露内部路径、堆栈、数据库结构等实现细节

## 不安全默认值

- TLS 校验是否被关闭（`InsecureSkipVerify`、`verify=False` 等）
- 加密算法是否使用了弱算法（MD5/SHA1 用于安全场景、ECB 模式等）
- 超时为零或无限时，是否让鉴权、校验或锁失效（单纯的资源耗尽按“默认不报告”处理）
- 默认密码、默认 token 是否可能出现在生产环境

## 信任边界违反

- 外部输入（HTTP 参数/header/body、文件内容、环境变量）是否未经校验直接传入内部逻辑
- 来自低信任来源的数据是否被当作高信任数据处理

## 输入校验缺失

- API 入口参数是否校验类型、格式、范围
- 文件上传是否校验类型、大小、内容
- 配置加载是否校验格式与合法值域

## 补充类别

- NoSQL 注入、XXE、模板注入、YAML 或 pickle 等反序列化执行
- JWT 校验缺失或算法可被替换、会话固定、会话失效不完整
- SSRF：只有攻击者能控制主机或协议时才成立，只控制路径不算
- XSS：反射型、存储型、DOM 型；React、Angular 等框架默认转义，只有使用 `dangerouslySetInnerHTML`、`bypassSecurityTrustHtml` 等绕过方法时才报告
- 证书校验被绕过、随机数不满足密码学要求
- 日志或响应中出现密钥、口令或个人敏感信息；记录普通 URL 和非敏感数据不算

## 方法

1. 先了解仓库已有的安全框架、校验和净化模式，以及项目的威胁模型。
2. 把新代码与已有安全模式对比，找出偏离、不一致和新增的攻击面。
3. 从用户输入追踪到敏感操作，检查跨越权限边界的路径。
4. 只报告本次差异新引入的问题，不报告已有的安全问题。

## 默认不报告

除非有具体、可达的攻击路径：

- 拒绝服务、资源耗尽、限流缺失、内存或 CPU 消耗、正则 DoS
- 已受保护的磁盘上的凭据；过时的第三方库版本（由依赖扫描单独处理）
- 非安全关键字段缺少校验、缺少加固措施或审计日志
- 理论上的竞态或时序攻击
- 内存安全语言中的内存安全问题；只用于测试的文件；文档文件
- 日志伪造、正则注入、把用户内容放进 AI 提示词
- 环境变量和 CLI 参数被篡改（视为可信输入）；UUID 被猜测
- 客户端 JS/TS 缺少鉴权（由服务端负责）
- Shell 脚本、GitHub Actions 工作流和 notebook 中的注入：只有能指出不可信输入如何到达时才报告

## 每条安全 finding 的要求

- 写明文件和行、类别（如 `sql_injection`）、利用场景（攻击者具体怎么做、得到什么）和修复建议。
- 逐条独立复核，排除误报；置信度低于 80 的不作为问题输出。
- P0：可直接利用并导致远程代码执行、数据泄露或鉴权绕过。P1：需要特定条件但影响显著。只在本地网络可利用的问题也可能是 P0。

## 判断原则

- 只记录有真实利用路径的安全问题，不报告纯理论风险
- 置信度不足时写"需补充上下文"，不武断判定为漏洞
- 不把"可以更安全"当成漏洞写入 findings
