# 条件审查模式

只读取差异命中的小节。描述的失败能到达用户时按 P0/P1 处理，否则作为建议。部分内容改编自 [tw93/Waza](https://github.com/tw93/Waza) 的 `check` 技能（MIT）。

## 目录

- 复发或难以观察的缺陷
- 按输出文本分支与异步完成
- 删除与精简
- 恢复和对齐历史差异
- 覆盖用户文件
- 删除与递归匹配范围
- 同一规则多处计算
- 测试是否覆盖真实入口
- 未发布功能的迁移代码
- 新引用的标识符
- 依赖与锁文件

## 复发或难以观察的缺陷

界面、布局、时序或有状态的缺陷再次出现时，再调一个常量不算有效覆盖。要求把判断抽成纯函数，用测试锁住被违反的不变量，例如宽度非零、命中区域半开区间、偏移有界。

不要求制造假接缝：浅层 helper 测不到调用点的真实失败时，把“没有合适的测试接缝”作为架构问题报告。对直接删除、提权、无界外部命令这类静默且代价高的原语，可以要求一个枚举调用点的测试，拒绝白名单之外的直接使用。

## 按输出文本分支与异步完成

代码根据错误信息或命令输出文本分支时，确认运行时这段文本里到底有什么：子进程继承 stdio 时，诊断可能显示在终端，而 `error.message` 里只有命令行。优先使用退出码或已知目标等结构化事实。

固定 `sleep`、`setTimeout`、帧数或猜测的超时代替可观察的完成信号时，标出来：它们随 CPU、刷新率和网络变化。改用回调、导航完成、状态标志或带超时的条件等待。

## 删除与精简

精简规则、提示词、技能或文档时，读回所有删除内容，把每处删除标为“并入 X”“与 Y 重复”或“行为被移除”，明确列出被移除的行为。删得多不代表精简得好。

判断死代码或用不到时，搜索整个仓库：入口、文档、测试、生成的分发表、脚本、CI、打包清单、manifest 和动态查找。区分只被测试引用和生产引用，追踪写入后只被间接读取的数据。搜索范围不完整不能作为删除依据。

## 恢复和对齐历史差异

差异恢复了最近删除的符号、字符串、资源、枚举值或配置字段时，确认当前主干仍在使用它；一致性测试或过期规则不能证明它还活着。

把一个与同类不同的例外改成和同类一致之前，先看引入这处差异的提交或注释：差异可能是在刻意规避已知缺陷，对齐后要保留这层保护。

## 覆盖用户文件

差异向用户已有的路径写入（`curl -o`、`>`、`tee`、先截断再写）时，问中途失败后还剩什么。先截断目标会让断网、超时或非零退出留下损坏文件且原件丢失。要求先写到同目录临时文件，内容完整后再替换。

临时文件只覆盖代码检查到的失败路径，覆盖不了信号：没有 trap 时，中断可能留下临时文件，或让脚本越过中断继续安装不完整的内容。`-fsSL`、`2>/dev/null` 或吞掉退出码会让用户不知道哪里坏了、原文件是否完好。

## 删除与递归匹配范围

递归、批量删除、遍历、ID 前缀通配或回退正则分支连到破坏性操作时，检查：

- 主分支和每个回退分支的匹配范围；
- 新入口是否覆盖受保护路径；
- 用户确认路径；
- 防护是否在删除原语内部，而不只在某个调用方。

只有精确标识符和精确路径可以授权删除；显示名称、厂商前缀、常见词和用户标签不能。

## 同一规则多处计算

分类、排序、阈值、计数或资格规则在两处独立计算时标出来：摘要与列表、预览与执行、评分与解释在一边修改后会漂移。要求两边使用同一个常量或纯函数；修改一边时搜索另一边。

## 测试是否覆盖真实入口

测试只覆盖生产代码走不到的 helper，或断言命令、配置的字面源码而不是实际发布的入口时，不算覆盖。问：它在未修复代码上会失败吗？用户执行的是它断言的那条路径吗？任一答案为否，测试本身就是问题。

还要问红绿运行回答不了的两个问题：

- 断言看不到什么：只匹配带标签实例的检查会把不带标签的实例当成豁免；在生产转换之前构造的输入集合永远不包含生产实际输出；比较两份副本的一致性检查看不到两份都缺的内容。
- 什么无害改动会让它变红：锚定在原文措辞、位置切片或某一种写法上的断言，会在改写时失败，却在真正的删除时通过。改为锚定事实、标识符或外围结构。

## 未发布功能的迁移代码

偏好、schema 或功能在当前未发布的工作中首次出现时，拒绝为它写迁移脚手架、按版本切换默认值或旧 key 兼容逻辑。与最近发布的 tag 比较；没有发布过的 key 直接走默认路径。

## 新引用的标识符

搜索差异假设已存在的每个函数、类型、变量、资源、命令目标和配置 key。在新差异之外找不到时，依赖未被证明。动态注册表要检查生成或查找路径，不能只靠名字匹配。

## 依赖与锁文件

- 在项目声明的环境中验证锁文件一致性：看完整 manifest、overrides、解析器配置和依赖差异，运行项目的 frozen/locked 检查。只在调查具体差异时才在隔离检出中重新生成。
- 新依赖不是差异明显需要的，标出来。反过来，声明了但全仓库零引用的依赖也报告给维护者，不擅自删除：它可能为后续功能预留；删除需要维护者同意、先证明零引用、删后完整构建。
- 自动安全 PR 额外检查两件事：机器人重写 manifest 时是否把非 ASCII 转义或重排了 key（与基线完整对比整个文件）；漏洞包是否真的进入发布产物（如 `cargo tree -i <pkg> --target all` 或对应的导入检查），不可达的锁文件条目不等于有效漏洞。
- 存在版本固定时，先用 `git log -S'<name>' -- <manifest>` 找到固定原因再动它；只升级主包而让配套固定留在旧版本，可能比不升级更糟。
