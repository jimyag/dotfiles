# Code Quality lane — 检查要点

## 目录

- 命名、函数规模与单一职责
- 错误处理、边界条件和逻辑正确性
- 回归、废弃迁移和可观测性
- 维护风险、测试覆盖和项目约定
- 结构维护性
- TypeScript/JavaScript 和前端专项
- 判断原则

## 命名

- 变量/函数/类型/包名是否清晰、一致，无意义缩写是否存在
- 布尔命名是否表达肯定语义（`isReady` 优于 `notDone`）
- 对外字段、枚举值、文案、日志和错误信息里的同一概念是否术语一致
- 命名是否混入临时实现细节、历史包袱或不该暴露到当前层的业务品牌

## 函数规模与单一职责

- 过长函数是否可合理拆分
- 重复逻辑是否可抽取为公共函数，但不要为了 DRY 引入过度抽象
- 参数列表过长时是否可用结构体收拢
- handler/controller/service/middleware 等层级职责是否清楚，通用鉴权、上下文注入、错误包装等逻辑是否放在合适层

## 错误处理

- 潜在失败点是否有明确的 error 检查与处理
- null/nil/零值边界是否有防御
- 错误信息是否可追踪（对内）、对外是否受控（不泄露内部细节）
- 业务错误、用户可恢复错误和系统错误是否区分清楚，错误码是否能被调用方稳定消费
- 错误包装是否保留足够诊断信息，避免排障时只剩模糊提示

## 边界条件

- 空集合、空字符串、nil 指针是否覆盖
- 越界访问、除零、整数溢出、off-by-one 是否考虑
- 极端输入（超大值、特殊字符、Unicode）是否有处理
- 重复提交、重试、幂等冲突、软删除、脏数据和并发请求场景是否有明确语义

## 逻辑正确性

- 条件判断是否反向或遗漏分支
- 状态机转换是否完整，是否存在非法状态
- 并发场景下共享状态的修改是否有序（非 Go 专项，Go 详见 go-specialist.md）

## 回归风险

- 是否改变了既有接口、默认值或配置语义
- 是否影响已有调用方的行为兼容性
- 是否将无关改动混入同一 diff（应独立提交）

## 废弃与迁移

- 删除旧逻辑、旧配置、旧 API 或旧工具前，是否确认还有哪些调用方、脚本、文档或用户依赖它
- 替代方案是否已经存在并覆盖关键用例；不要在没有替代路径时只留下 deprecation 文案
- 迁移是否有可执行路径，例如兼容窗口、自动迁移、双写/双读、告警、文档或回滚方案
- 是否错误地把“代码看起来没用”当作“没人依赖”，尤其是 CLI、配置字段、环境变量、脚本入口和导出 API

## 可观测性

- 生产路径新增后台任务、外部调用、队列、重试、缓存或状态转换时，是否能回答“它是否在工作、失败在哪里、影响多少”
- 日志是否是稳定事件和结构化字段，而不是难以查询的 prose；错误码、request id、资源 id 是否足够定位
- 指标是否避免高基数标签；告警是否对应用户影响或明确 SLO，而不是任意内部计数
- fallback、重试、降级和跳过逻辑是否可见；静默成功通常会把线上问题拖到用户报告后才暴露

## 未来维护风险

- 改动是否只是“当前能跑”，但依赖隐式前提，例如特定执行顺序、本机路径、单一调用方、固定数据规模或外部状态
- 是否新增隐藏副作用，例如修改全局状态、缓存、环境变量、工作目录、日志级别、后台任务、文件或网络资源
- 是否存在静默 fallback、吞错、默认值兜底或自动修复，看似更健壮但会掩盖真实不变量
- 命名是否会误导后续维护者，例如把生成物说成源数据、把一次性操作命名成幂等操作、把临时路径命名成稳定配置
- 是否引入难以删除的临时分支、重复 helper、薄封装或跨层依赖，导致以后每次修改都要同步多处认知

## 测试覆盖

- 关键路径和失败路径是否有测试
- 声称"已验证"的结论是否有对应测试或可复现手段作为证据
- 新增边界条件是否补充了对应测试用例
- 测试是否依赖执行顺序、共享状态、未提交事务、异步竞态或外部环境，导致换环境后不稳定
- 删除或收缩测试时，是否明确保留了原本覆盖的关键约束
- reviewer 已指出的 bug 场景修复后，是否补了专门的回归测试

## 项目约定

- 是否符合仓库已有命名、目录结构、接口约定
- 是否遵守 CLAUDE.md 或项目内已有规范
- 不要为"更优雅"而单方面偏离当前项目风格

## 结构维护性（Deep 审查追加）

> 仅在主流程标记为 Deep，或用户明确要求严格维护性审查时执行。

- 是否能用更直接的结构删除分支、模式、helper 或层级，而不是把复杂度搬到别处
- 是否新增零散 special-case、临时 flag、模式分支或 ad-hoc 条件，导致原本清晰的流程更难推理
- 文件是否因本次改动从 1000 行以内膨胀到超过 1000 行；若是，是否有强理由不拆分
- 新增抽象、wrapper、adapter 是否真正减少调用方复杂度；薄封装、身份转发、只改名不改语义的层级应谨慎
- 逻辑是否放在拥有该概念的 canonical layer；不要把 feature-specific 逻辑泄漏进共享路径或基础设施层
- 是否复用了仓库已有 canonical helper、服务或类型，而不是新增近似重复实现
- 类型边界是否清晰；不必要的 `any`、`unknown`、类型断言、可选字段或静默 fallback 是否掩盖了真实不变量
- 相关更新是否可能半成功半失败；如果存在明显的原子性边界，是否应收敛为更一致的流程
- 独立工作是否被无理由串行化；仅当并行化能让编排更简单、更可靠时才作为 finding

## TypeScript/JavaScript 轻量专项

> 仅在检测到 `package.json`、`tsconfig.json`、`.ts`、`.tsx`、`.js` 或 `.jsx` 时执行。

- 是否遵守项目既有 TS/JS 约定（如 `type`/`interface` 偏好、模块格式、import 排序、文件扩展名）
- 是否引入不必要的 `any`、类型断言或类型擦除，导致调用方失去静态检查
- 新增导出类型、组件 props、API 响应类型是否足够明确
- 未使用变量、参数的处理是否符合项目约定，不为绕过 lint 引入噪音命名
- React/前端代码中 props、state、effect 依赖是否清晰，是否存在明显 stale closure 或多余重渲染风险

## 前端交互与文案轻量检查

> 仅在改动涉及 UI、文案、前端状态或浏览器行为时执行。

- 用户操作路径是否完整，成功、失败、空态、加载态、刷新态和 stale 态是否可解释
- 页面文案是否使用产品内已有术语，避免把实现状态或内部错误直接暴露给用户
- 布局和交互改动是否增加理解成本，例如按钮位置、弹窗确认、跳转或刷新行为变得不符合已有习惯
- 外链和新窗口行为是否符合浏览器与安全约束，例如需要时使用 `noopener`

## 判断原则

- 只记录明确影响正确性、可维护性或项目一致性的问题
- 纯主观风格偏好（缩进风格、空行数量等）不写入 findings
- Deep 结构维护性问题需要指出具体复杂度来源和可执行替代方案；不要用"可以更优雅"这类泛化理由制造 findings
