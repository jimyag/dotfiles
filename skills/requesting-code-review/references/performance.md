# Performance lane — 检查要点

## 性能声明与测量校验

PR 声称吞吐、延迟、内存或 CPU 改善，或差异疑似引入退化时，先检查项目现有基准入口、测量脚本和实际结果。审查保持只读；使用已有产物，确需运行时仅在授权允许且不会修改被审工作区或影响共享服务的隔离环境中执行。不为性能审查擅自压测生产或安装工具。

- 将声明转成可比较的工作负载和指标：相同输入、数据量、并发、构建模式、调优条件及冷/热缓存。对比变更前后的代码；不同环境或不同工作量不能直接归因于 diff。
- 核对工作确实在计时区间完成：异步操作已等待、惰性结果已消费、必要的持久化已完成，并检查实际完成量和结果正确性。失败、拒绝、提前返回或空操作不能算加速。
- 同时读取错误、超时、重试和资源消耗；检查压测端是否先饱和。用独立采样定位主要瓶颈，不把追踪开销混入报告数字。
- 对方案比较检查 A/B 交替重复测量、中位数和波动范围；差异在噪声内时不宣称提升。单次运行只能标为粗估。
- 核对数量级和端到端意义：局部耗时占比、资源上限是否能解释收益。微基准只支持对应局部结论，不能直接证明用户等待时间改善。
- 证据缺失时附最小复跑命令、预期指标和缺口，标为未测量或收益未证实；源码已能证明的可达退化保留为 finding 或待确认，不因无法压测而删除。缺少性能数据本身不自动等于代码缺陷。

性能项报告指标与单位、负载、对照版本、次数、波动、正确性和完成量证据；明确哪些实际运行、哪些仅核查已有结果、哪些仍是静态推断。

## 重复工作

- 循环体内是否有可提取到循环外的重复计算
- 重复解析同一数据（JSON、正则、模板）是否可缓存
- 同一请求中对相同资源的重复查询是否可合并

## 复杂度退化

- 是否引入 O(n²) 或更差的嵌套循环
- 排序、查找是否使用了合适的数据结构（map vs 线性扫描）
- 递归是否有尾调用或记忆化机会

## 过度分配

- 热点路径中是否有不必要的大对象或临时对象创建
- 字符串拼接是否用了低效方式（循环 `+` 而非 Builder/Join）
- 大 slice/map 是否预分配了合理容量

## I/O 与网络放大

- 是否存在 N+1 查询（循环中逐条请求数据库或 RPC）
- 批量操作是否可以合并为单次调用
- 响应体是否可以流式处理而非全量加载到内存

## 缓存与批量机会

- 高频只读数据是否有缓存层，TTL 是否合理
- 外部调用结果是否在请求生命周期内复用
- 批量写入是否比逐条写入更合适

## 热点路径锁粒度

- 是否有可以缩小的临界区
- 读多写少场景是否可改用 RWMutex 或无锁结构
- 是否有不必要的全局锁

## 判断原则

- 只在存在明确性能影响或已知热点路径上报告问题
- 非热点路径的"理论上可以优化"不写入 findings
- 优化建议应具体（指出位置和方案），不泛泛而谈
