# Review 范围与完整性预判

## 目标与需求

- 将改动标记为 `目标一致`、`范围漂移` 或 `不完整`。
- 有关联 issue、ticket 或 PRD 时，提取需求、验收标准、非目标和人工验证项，再对照 diff。
- 需求来源按顺序查找：PR 描述和提交信息中的 issue 引用（`#123`、`Closes #45`）、用户给出的路径、`docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的文档。缺少必要的验收条件时向用户核实。
- issue 要连同评论一起读。以最后确认的需求为准，原文与讨论冲突时先核对。涉及权限、公开接口或配置时，同时读相关设计文档、ADR 和接口文档，确认权限归属和调用方式是既定决定还是本次新引入。
- 将 PR 描述和提交信息逐条与差异对照，发现出入时核实实际行为。
- 需求轴的每条发现引用需求原文，分三类：要求了但缺失或不完整；差异中有但没要求（范围漂移）；看似实现了但实现有误。
- 判断“实现有误”时，用需求里明确的默认值、边界输入、错误、权限主体和已有数据场景亲自运行验证。先核实含糊的验收条件，再判断实际结果是否违反需求。
- 没有关联需求时，只使用 PR 描述、提交信息和 diff，不臆造目标。
- 仅当多个主题没有代码依赖、能独立 review/merge 且拆分能降低真实风险时建议拆分。
- 每个变更文件和新增公开面都应能用一句话追溯到目标；说不出的文件、依赖、配置项、抽象、生成物、工作流权限或发布行为先视为范围漂移。
- 新增配置项、参数、环境变量、命令或服务时，问谁会改它、为什么一个正确的默认值满足不了他们；没有证据表明存在不同用户需求时，按范围漂移处理，建议改默认路径。
- 差异里提交了审查报告、评分卡或诊断快照时，它们是证据而不是长期文档：建议提炼其中稳定的规则放进项目指导文件，不提交快照本身。

## 完整性

- 模式修复要搜索 sibling pattern，并核对哪些同类调用能复现相同问题。
- 检查契约是否同步到调用方、配置、文档、生成物和验证证据。
- 生产路径新增 I/O、重试、队列、后台任务或跨服务调用时，检查日志、指标和错误语义。
- 安全边界、权限、 destructive path、迁移和兼容策略缺失时提升优先级。

## 双轴与反证

- `需求轴`：目标、范围、兼容性、生成物、文档和验证是否完整。
- `工程轴`：正确性、可维护性、性能、安全、测试和项目约定。
- 两个轴都用于寻找候选。报告已复现的问题时，写出违反的具体需求或工程约束。
- 输出前寻找能直接推翻 finding 的当前 diff 或上下文证据，存在反证时删除。
