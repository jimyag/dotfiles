# 检查角度

候选简化较多、需要比较取舍时使用；简单局部清理不必读取。

## 复用

- 新增的 helper、类型、常量或转换逻辑先在共享工具模块和改动相邻文件中搜索定义与调用方；已有承担相同职责的实现时，指出应调用的具体符号。
- 名称相似但默认值、错误处理、输入范围或副作用不同，不足以证明可以复用；替换前列出语义差异。

## 简化

- 降低不必要的嵌套、分支和中间状态；能由其他字段推导的状态不单独保存。
- 删除近似复制的代码块、无价值的包装、只复述代码的注释，以及本次改动遗留的死代码和未用参数。
- 使用能表达职责的变量名和函数名；合并紧密相关的逻辑，同时保持独立职责分离。
- 遵循项目已有的导入、类型、错误处理和命名约定。
- 多条件判断优先使用清楚的 `if`/`else` 或 `switch`，避免嵌套三元表达式。

## 效率

- 重复计算、重复解析或对同一资源的重复 I/O，可以提到循环外或在一次调用内复用。
- 互不依赖的操作被串行执行，或在启动路径、热路径上新增了阻塞工作。
- 长期存活的闭包或回调捕获了整个外层作用域，使大对象无法释放；只保留实际需要的字段。
- 只在能说明具体代价时提出；非热路径上“理论上更快”的改法不作为候选。改为并发或调整执行顺序会改变行为，只报告不实施。

## 修复深度

- 在共享函数、中间件或公共配置上为单个调用方叠加特例，通常说明修复没有落在根因处。指出应修改的底层机制，并检查该机制的全部调用方。
- 修改底层机制会改变其他调用方的行为时，作为单独变更报告，不在本轮简化中实施。

## 不要为了减少行数

- 删除有助于组织或隔离变化的有效抽象；
- 引入密集单行代码、隐式控制流或难以调试的技巧；
- 把多个独立职责塞进一个函数或组件；
- 改变错误类型、日志、副作用顺序、并发顺序或兼容性。

判断标准是维护者是否更容易理解、验证和修改，不是差异是否更短。
