# 清晰度检查

候选简化较多、需要比较取舍时使用；简单局部清理不必读取。

优先考虑：

- 降低不必要的嵌套、分支和中间状态；
- 删除重复逻辑、无价值的包装和只复述代码的注释；
- 使用能表达职责的变量名和函数名；
- 合并紧密相关的逻辑，同时保持独立职责分离；
- 遵循项目已有的导入、类型、错误处理和命名约定；
- 多条件判断优先使用清楚的 `if`/`else` 或 `switch`，避免嵌套三元表达式。

不要为了减少行数：

- 删除有助于组织或隔离变化的有效抽象；
- 引入密集单行代码、隐式控制流或难以调试的技巧；
- 把多个独立职责塞进一个函数或组件；
- 改变错误类型、日志、副作用顺序、并发顺序或兼容性。

判断标准是维护者是否更容易理解、验证和修改，不是差异是否更短。
