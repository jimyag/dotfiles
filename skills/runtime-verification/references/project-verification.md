# 项目验证配方

用户要求沉淀验证入口、维护已有入口，或项目约定要求时使用。优先更新已有项目文档或验证技能，不另建平行入口。没有沉淀需求时只执行本次验证。

## 留给下一个会话的信息

- 启动：实际构建和启动命令、必需配置、迁移和种子数据、实例版本，以及可用的就绪条件。端口能连接不代表初始化已完成。
- 健康检查：只读确认当前实例属于本次运行、版本正确、认证有效且可继续驱动。操作异常后重新检查；进程健康但会话失常时重置到已知状态或重新启动。
- 驱动：真实用户入口、稳定的选择器或命令、前置状态，以及可观察的终态。副作用同时检查文件、数据库或其他实际结果。
- 功能索引：按已有场景 ID 或功能入口连接到驱动配方；记录各入口的前置条件，不复制现有场景契约。多个入口不能用其中一个的成功代表全部通过。
- 隔离与清理：独立端口、数据目录或会话，只结束本次启动的进程。失败迭代同样清理残留；证据放在不会随实例清理删除的位置，清理后再次确认。

命令和路径来自当前仓库，不留下占位步骤。dry-run 或测试模式实际会跳过什么，要通过状态和副作用确认，不能只凭名称判断。

## 交付前执行

按配方完成启动、健康检查、至少一个相关功能、捕获证据和清理。未经实际执行的配方标为草稿；替代环境验证不能覆盖真实目标独有的安装、设备或认证步骤。

## 维护已有配方

对本轮受影响功能逐项核对源码入口和实际运行结果。仅修改配方时，遇到产品行为不符应区分文档漂移和产品回归：以需求、现有契约和变更意图为依据，不把失败预期改成成功来让文档通过。只更新有证据的步骤，不顺带修改产品代码。

完整性检查只有在用户要求维护整个验证入口时才覆盖全部功能；无法到达的功能写出尝试入口、缺少的前置条件和未验证部分。
