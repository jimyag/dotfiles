# Design Doc 与 ADR 路由

只有决策会长期约束实现、选错代价高或需要多人先达成共识时，才增加设计文档流程。

## Design Doc

满足以下任意两项时，建议先用 `technical-writing` 补设计文档：

- 改动复杂、高风险、跨团队或目标仍不清楚。
- 实现会长期运行，返工、迁移或回滚成本高。
- 涉及接口、数据、权限、存储、部署、兼容性或外部依赖。
- reviewer 需要在实现前确认目标、非目标、约束、场景或备选方案。

## ADR

满足以下任意两项时，建议用 `architecture-decision-record` 评估或创建 ADR：

- 比较过真实备选方案。
- 接受了明确且非平凡的成本。
- 决策不容易回滚或会影响后续设计。
- 缺少“为什么”会让未来维护者难以判断约束来源。

低成本、可随实现调整的细节不需要 Design Doc 或 ADR。
