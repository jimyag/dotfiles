# 高级排障模式

## 构造反馈环

大致按以下顺序尝试，选第一个能命中故障路径的：

1. 在能到达缺陷的接缝上写失败测试（单元、集成或 E2E）。
2. 对运行中的开发服务发 HTTP 请求的脚本。
3. 用固定输入调用 CLI，把输出与已知正确的快照比较。
4. 无头浏览器脚本驱动界面，断言 DOM、控制台或网络请求。
5. 回放抓取到的真实请求、负载或事件日志，在隔离环境中走同一路径。
6. 临时搭一个最小子系统（单个服务、依赖用替身），一次调用就能走到缺陷路径。
7. “偶尔输出错误”时做属性或模糊测试，跑上千个随机输入找失败模式。
8. 缺陷出现在两个已知状态之间时，把“切到状态 X、检查”自动化，用 `git bisect run` 驱动。
9. 差分：同一输入分别跑旧版本和新版本（或两种配置），比较输出。
10. 最后才是人工参与：需要人点击时，写一个结构化的引导脚本让人按步骤操作并回传输出。

反馈环本身也要打磨：能否更快（缓存准备步骤、跳过无关初始化、缩小测试范围）；信号能否更准（断言具体症状而不是“没崩溃”）；能否更确定（固定时间、固定随机种子、隔离文件系统和网络）。30 秒且不稳定的反馈环几乎等于没有。

非确定性缺陷的目标是提高复现率，而不是一次干净复现：循环触发上百次、并行、加压、缩小时序窗口。50% 复现率可以调试，1% 不行，继续提高直到可调试。

确实建不起反馈环时明确说明，列出已尝试的方法，并向用户要：能复现的环境访问、脱敏后的抓取材料（HAR、日志、core dump、带时间戳的录屏），或在生产环境加临时观测的许可。没有反馈环时不进入假设阶段。

## 回归与对照

用户说“以前正常”“还是不对”或提供旧截图、旧版本和旧产物时：

1. 列出全部症状和最近已知正常基准。
2. 在修改前定义通过/失败检查。
3. 对比相关路径、配置、生成物和运行状态。
4. 同一症状在一次修复后仍存在时，停止叠补丁并重建假设。

## 二分定位

1. 先保护当前工作区；`git status --short --branch -uall` 有任何修改、暂存或未跟踪文件时，在临时 detached worktree 中二分，结束后删除；无法创建时先询问。
2. 先读正常版本到当前版本的相关路径差异，范围很小时不必完整 bisect。
3. 必须有非交互、可重复的通过/失败命令。
4. 直接测试某个嫌疑提交时也用 `git bisect good/bad` 记账；结束后先 `git bisect reset`，再删除临时 worktree。
5. 找到嫌疑提交后，继续定位触发回归的具体条件，不把提交本身当完整根因。

## 同型缺陷搜索

修复可重复的模式问题后，提炼函数、调用形状、锁、选择器、输入或校验缺口，在仓库内搜索同类命中，排除生成目录、构建产物和第三方依赖。类缺陷（如“处理函数缺少加锁”）要搜周围结构，不只搜字面文本。逐项标记为同类问题、安全例外（写原因）或仍需确认，不静默跳过任何命中，也不因一次 grep 命中自动扩大修改范围；与本次无关的问题列出，经用户同意再修。

## 回归测试红绿验证

先判断有没有正确的接缝：测试要能在调用点按真实方式触发缺陷。唯一可用的接缝太浅时（缺陷需要多个调用方而测试只有一个、单元测试复现不了触发缺陷的调用链），在那里加测试只会带来虚假的信心；这时把“没有正确接缝”记为发现，作为事后追问的架构建议。为了让测试变红而改动代码或夹具时，先与原始副本 `diff`，证明改动确实生效再相信这次红。

问题曾经修过又复发时，修复要带回归测试，并且：

1. 测试放在项目测试套件中，不放临时文件。
2. 实际运行过红绿：在隔离的临时检出或夹具里，对未修复代码运行一次看到失败，再对修复后代码运行看到通过。不要为了对比去 revert 或 stash 共享工作区。只见过通过的测试什么也没固定住。
3. 防止假绿：确认中途失败的断言会让整个测试失败，而不是只有最后一条断言生效（Shell 测试尤其要用两行最小例子实际验证）；“输出不包含 X”这类否定断言要配一个能失败的肯定断言，否则 X 从未出现时它永远通过。
4. 提交信息说明为什么复发，以及这次修复为什么能防止复发。

## 运行时证据阶梯

按成本与证据强度逐步检查：

1. 源码路径和状态转移；
2. 最小稳定复现；
3. 日志、缓存、生成物或外部系统状态；
4. 针对性测试和构建；
5. 用户可观察的真实运行结果。

无法到达更高层级时保留未验证边界，不用低层证据替代高层结论。

## 定向日志

加日志前写清它要区分的假设。优先记录分支、旧值/新值、输入键、错误码、顺序和关联 ID。日志放在能区分路径的位置，不在症状点无界堆积。

## 低层基线

- 界面异常：区分 DOM/CSS/渲染、数据和状态层。
- 网络异常：先确认 DNS、代理、证书、端口、服务发现和服务端响应。
- 工具链异常：先确认版本、路径、环境变量和最小命令。
- 生成物异常：先确认源文件、生成命令、输出路径和时间戳。
- 写状态流程：检查重试、重启、中断恢复和重复执行能否收敛到同一终态。
