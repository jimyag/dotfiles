# Project Submission Evaluator

开始时声明："我正在使用 project-submission-evaluator skill 做源码级项目评估。"

## 目标

对一批项目做可复核的源码级评估。结论必须来自实际代码、入口、测试、配置和运行证据；README 只能作为线索，不能作为评分依据。

## 适用场景

- 比赛、作业、黑客松或候选项目批量评分。
- 用户要求按 rubric 给分、排序、生成 Markdown/TSV/JSON。
- 用户要求多个 reviewer 互相比较并整合优点。
- 用户要求把某次评审规则沉淀为可复用流程。

## 不适用场景

- 单个 repo 的普通 code review；用 `requesting-code-review`。
- 只要可运行性排障；用 `systematic-debugging`。
- 只要 GitHub issue/PR 摘要；用 `gh-view`。

## 执行流程

1. 规范输入
   - 把用户给的 repo URL、路径、名称和 rubric 保存为本轮上下文。
   - 如果用户给了顺序，保存原始顺序；后续 TSV/表格必须按这个顺序输出。
   - URL 匹配时只规范化 `.git` 和尾部 `/`，输出仍保留用户原始 URL。

2. 获取源码
   - clone/fetch 每个 repo 或读取本地路径。
   - 记录无法获取的项目和原因，不用 README 代替源码评估。
   - 对非 git URL 或空仓库单独标记。

3. 建立 source profile
   - 文件清单、语言/框架、入口点、核心实现、测试、配置、依赖和运行脚本。
   - 搜索关键需求信号，再抽样读取代表性源码。
   - 对核心功能缺失、mock 代替实现、只有 UI 壳、硬编码演示等情况明确记录证据。

4. 严格评分
   - 先按 rubric 给初评，再做校准。
   - 基本合规通常低于 `3`；`>=3` 需要多个可证明的拉升因素，例如核心功能完整、真实集成、测试/错误处理、可运行性、体验或工程质量。
   - 分数可下调，但必须是针对证据的校准，不做机械统一扣分。
   - 保存校准前结果，便于回看分数变化。

5. 多 reviewer 仲裁
   - 用户要求多个 agent 或多视角时，拆成专门 reviewer：实现完整性、可运行性、工程质量、产品契合度等。
   - 最终必须有 central arbitration：合并证据、消除重复、解释分歧，不要把多个 reviewer 输出直接拼接。

6. 产物
   - Markdown report：每个项目给优点、不足、关键证据和分数。
   - TSV/CSV：按用户指定顺序输出 `仓库\t分数\t原因`，不重排。
   - JSON：保留结构化结果和证据路径。

## 验证

- 检查所有输入项目都有结果或明确失败原因。
- 抽查 TSV 顺序与用户输入顺序一致。
- 检查 Markdown、TSV、JSON 的分数一致。
- 检查 `>=3` 的项目是否都有足够源码证据支撑。
- 明确哪些结论来自源码，哪些只是 README 或文档线索。

## 输出契约

```text
## 结果
- 已评审:
- 拉取失败:
- 输出文件:

## 校准
- 评分标准:
- 严格程度:
- 边界案例:

## 验证
- 已检查源码:
- 顺序已保留:
- 分数一致性:

## 可复用规则
- 提升为 skill:
- 保留为批次特定:
```

## 关键约束

- 不要只看 README。
- 不要把一个批次的具体 repo、分数或结论写进可复用 skill。
- 不要声称用了 sub-agent，除非实际启动了独立 agent；shell 并行和多文件扫描不等于 sub-agent。
- 派生 TSV 必须来自最终裁定结果，不要单独维护一份可能漂移的表。
