# 中文技术文案编辑规则

本参考用于中文技术文档、产品能力说明、API 文案、界面文案、操作步骤和故障排查。它补充 `style-aware-editor` 的场景规则，不替代目标项目自己的术语表、品牌规范或事实来源。

## 目录

- 适用边界
- 规则优先级
- 事实与确定程度
- 操作步骤和故障排查
- API、状态和错误文案
- 术语与排版

- 来源与许可

## 适用边界

完整应用于：

- 安装、部署和操作步骤；
- 故障排查、运维 Runbook 和安全说明；
- 多步骤 API 调用流程；
- 参数、状态、错误码和恢复提示。

选择性应用于 FAQ、更新日志、产品能力说明和界面文案。品牌稿、叙事文章、法律原文、正式引用和需要保留作者风格的文本，不要机械改成操作手册。

代码、命令、路径、URL、API 路径、JSON 键、字段名、枚举值、配置项和用户指定的固定字面量属于受保护内容。

## 规则优先级

发生冲突时按以下顺序处理：

1. 保留事实、逻辑、限制、安全信息和法律含义。
2. 服从用户明确要求和目标项目约定。
3. 保持技术术语和机器可读内容准确。
4. 改善信息顺序、语义、语气和可扫读性。
5. 最后处理标点、留白和大小写。

不要为了句子更短、语气更肯定或格式更整齐而牺牲高优先级信息。不设固定的句长、段长或名词数量上限，英文受控语言的词数限制不适用于中文；已经清楚的句子保持原样。

## 事实与确定程度

- 不新增来源没有提供的数字、日期、时限、SLA、能力、条件、因果关系或结论。
- 不删除前置条件、适用范围、例外、风险、单位、默认值、兼容性和失败处理。
- 保留条件是必要还是充分。「只有检查通过，才允许重启」规定重启的前提；改成「检查通过后重启」，就变成每次检查通过都要重启。调整语序时，不要把条件或限定语挪到它不约束的动作上。
- 保留「全部」「任一」「和」「或」「除……外」的作用范围。改成列表前先确认每个限定语管到哪一项：「所有者或编辑者经审批后可以删除项目」没有说清所有者是否也要审批，先确认再拆。拆句时不要把可选项改成必经步骤；「否则」分支要写清判断的是没有执行还是执行未成功，「自动恢复未成功时通知值班」不能改成「未开启自动恢复时通知值班」。
- 保留要求、建议、允许和能力的区别，以及「可能」「计划」「通常」「预计」表达的确定程度。「建议检查报告」改成「检查报告」会加重要求，「请求可能失败」改成「请求失败」会提高确定性；已排队、已开始和已完成的动作不能互相替换。同一份文档里，同一要求强度沿用同一个情态词，例如强制写「必须」、禁止写「不得」、允许写「可以」；原文强度不明时保留原词并标记，不擅自统一。
- 支持范围、受影响对象、所需权限和错误清单不用「等」「之类」收尾；来源没有给出完整清单时标记「待确认」。
- 信息不足或一句话有多种读法时，审查写出各种读法，改写保留原句并标记「待确认」或提出具体问题；不要默默选择最容易改写的读法，也不要自行补成看似完整的事实。
- 区分人工操作和系统自动行为；不要把系统结果改写成读者必须执行的步骤。
- 同一对象、状态和动作使用同一首选术语，不为避免重复而轮换同义词。相近的词不一定指同一事物：「检查地址」和「确认投递」是两个动作，系统区分「取消」「超时」「失败」时也要保留三个词。

## 操作步骤和故障排查

操作说明默认按以下顺序组织：

1. 前置条件。
2. 风险、限制和停止条件。
3. 按实际顺序排列的编号步骤。
4. 每一步可观察的预期结果。
5. 失败后的恢复方式或需要收集的诊断信息。

编辑时遵循：

- 一个步骤只包含一个主要动作；不可分割或必须同时完成的动作可以保留在同一步。
- 拆分步骤时保留前一步的完成条件。「上传完成后，删除本地文件」拆成「开始上传。删除本地文件。」后，读者可能在上传结束前删除文件。只给真正有先后关系的动作编号，不为可选项制造顺序。
- 读者执行前必须知道的条件和警告放在动作之前，不要藏在句末括号中。警告先写必须做或不得做的事，再写不遵守的后果。
- 写清执行者、动作对象和预期结果，避免无法定位的「该」「其」「此」「上述」「相关」。来源无法确定执行者或指代对象时标记歧义，不为改成主动句自行补出执行者；「worker 通知 scheduler 后，它会重试」需要先确认是谁重试。
- 故障排查先安排低风险、可逆、证据价值高的检查，再根据证据给出原因。
- 将现象、证据、可能原因、操作和结果分开；不要把「可能原因」改写成「确定原因」。
- 保持否定范围明确，让读者知道禁止的是哪个动作、对象和时间段；不用双重否定，「不能不确认」写成「必须确认」。

## API、状态和错误文案

- 先确认状态在当前接口中的真实含义，再选择中文；不要给英文状态词建立脱离语境的唯一翻译。
- 区分 HTTP 状态、业务状态、任务状态和界面提示。
- 不修改状态码、枚举值、字段名和响应原文。
- `Invalid` 根据语义写成「无效」「格式有误」或「校验未通过」，不要默认翻译成「非法」。
- `Unauthorized` 根据原因写成「未登录」「认证未通过」或「缺少认证信息」，不要机械翻译成「未授权」。
- `Forbidden` 可以写成「无权限访问」或「当前不允许访问」；`Accepted` 可以写成「已受理」或「已接收，等待处理」。
- 错误文案优先说明：发生了什么、哪个对象受影响、可能原因、恢复操作，以及仍失败时需要提供的诊断信息。
- 不在没有依据时承诺恢复时间，也不把推测写成确定原因。
- 只改措辞时，不补来源没有的原因、恢复操作或要求：「连接超时」不能改成「密码错误，请重新登录」，「导出可能不完整」也不等于要求重试或做完整性检查。用户要求补充内容时，以源码或实际行为为依据，并和原文内容分开交代。

参数说明尽量覆盖：类型和格式、是否必填、单位、默认值、允许范围、缺省行为，以及与其他参数的依赖或互斥关系。避免「正常值」「根据情况填写」「相关信息」等无法执行的说明。

## 术语与排版

- 目标项目术语表和产品官方写法优先；多义词先判断语境，不做全局替换。界面上的实际文案优先于更好懂、但用户在屏幕上找不到的同义词。
- 读者可能不熟悉的专用词在首次出现处定义，定义只用来源给出的含义；不为每份输出附术语表。
- 名词串先还原名词之间的关系：「worker 任务取消策略」可能是取消 worker 任务的策略，也可能是 worker 取消任务时使用的策略，没有证据时不选读起来更顺的那种。界面短标签和既定术语不当作病句改写。
- 把「对 X 进行修改」「予以 X」「加以 X」「做好 X 工作」「完成 X 的操作」「作出 X 决定」「通过 X 的方式」改成直接动词；「实现 X 功能」写出 X 的具体行为，「存在 X 问题」写出具体现象，「有一定的 X」写出具体的量，没有量时删除。改写后要求、能力和时态不能变：「客户端必须进行校验」可以改成「客户端必须校验」。
- 中文正文默认使用全角标点；中文引号默认使用 `「」`，但项目、地区、出版或引用规范可以覆盖。
- 可见正文中的中文与英文缩写、独立数字和版本号通常保留空格；代码、路径、字段、命令和官方产品拼写不机械处理。
- 检查数字是否带单位，百分比和百分点是否混用，区间边界是否明确。
- 高置信度错词可以直接修正，例如「阀值」改为「阈值」、「布署」改为「部署」、「反回」改为「返回」、「回朔」改为「回溯」。
- 「登录/登陆」「配置/配制」「截至/截止」「认证/授权」必须结合语境判断，不能作为无条件替换规则。
- 黑话只有在有明确业务定义、属于正式术语或引用原文时保留；否则写出具体对象、动作、状态和完成条件。

## 项目覆盖

开始编辑前，先检查目标项目的 `AGENTS.md`、术语表、品牌规范、相邻文档和用户指示。项目覆盖可以规定：

- 产品和版本的正式写法；
- 首选术语与允许例外；
- 品牌语气、称呼、引号和标点；
- 文档结构、API 说明和故障排查格式；
- 必须原样保留的法律、安全、兼容性和弃用文本。

示例约定不能自动成为目标项目规则。缺少经过确认的覆盖时，使用本参考的克制默认值。

## 最终检查

- 是否新增了来源不明的日期、数字、时限、能力或结论？
- 是否遗漏了条件、例外、风险、单位、默认值或恢复方式？
- 主语、对象、否定范围、因果关系、要求强度和确定程度是否保持准确？
- 按读者要做的决定逐句对照原文：谁对什么执行动作、在什么条件下、按什么顺序、得到什么结果？改写版允许了原文排除的动作，或排除了原文允许的动作时，交付前修正。
- 操作是否按执行顺序排列，每一步是否有明确动作，依赖前一步的动作是否保留了完成条件？
- API 状态和错误文案是否来自实际语义，而不是逐词翻译？
- 同一概念是否使用同一术语？
- 代码、路径、字段、命令、引用和固定字面量是否保持原样？
- 项目覆盖是否来自目标项目，而不是示例或当前 skill？
