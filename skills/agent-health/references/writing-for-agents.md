# 给代理写文档

审计或改写技能、`AGENTS.md`、`CLAUDE.md` 以及被它们引用的文档时使用。目标是让代理每次走同一套流程，而不是每次产出相同文字。

## 目录

## 指针与两种负担

指针是常驻上下文中、指向不在上下文里的材料并写明何时去读的那句话。技能的 `description` 是指针，`AGENTS.md` 中“遇到 X 时读 docs/y.md”也是。决定代理何时、多可靠地去读材料的是指针的措辞，而不是目标内容。必需的材料挂在措辞含糊的指针后面，是可靠性问题：先改措辞，改不好再把材料放进正文。

- 关键词放在最前面，那是触发发生的位置。
- 每个分支只写一个触发；同一分支的同义说法合并。
- 删去正文已经说明的身份描述。

每加一份文档或一行指针都要付出一种成本：

- 上下文负担：常驻内容（`AGENTS.md` 的行、技能描述）每轮都占用窗口和注意力，不论是否用到。
- 认知负担：人需要记住有哪些文档、什么时候用。这是保留人的判断所付的代价，花在需要人判断的地方，其他地方去掉。

## 信息层级

文档由两类内容组成：步骤（按顺序执行的动作）和参考（按需查阅的定义、规则、事实）。按代理需要它的紧迫程度排列：

1. 正文中的步骤：要做什么，按顺序。
2. 正文中的参考：按需查阅；同一层级的平铺规则清单是正常结构。
3. 拆出去的参考：放在单独文件里，由指针触发才加载。

推下去太少，正文臃肿；推下去太多，代理需要的材料被藏起来。判断方法看分支：每个分支都需要的留在正文，只有部分分支用到的放到指针后面。有步骤的文档里，混入应拆出的参考会埋没步骤，让步骤是否被执行变得随机。

同一概念的定义、规则和例外放在同一个标题下，不要分散；分散和重复不同，重复是同一意思写两遍，分散是一个意思拆成几块。

文档过长时，即使每行都有用，注意力也会被摊薄。办法是拆出参考，按分支或顺序拆分，让每条路径只带自己需要的内容。

## 步骤与完成条件

每一步都以完成条件结束：

- 清晰：代理能分辨做完和没做完吗？“理解清楚”这类模糊条件会导致过早结束。先把条件改清楚；条件本身无法更清楚、且确实观察到代理赶进度时，再把后续步骤拆到真正的上下文边界之后（交接或子代理），内联调用不算边界。
- 要求：“每个修改过的模型都已核对”比“给出变更清单”逼出更多实际工作。要求不只针对步骤，“每条规则都已应用”同样约束一组平铺的参考。

最好的完成条件既可检查又要求穷尽。

## 何时拆分

拆分会增加一种负担，只有值得时才拆：

- 按顺序拆：后续步骤让代理急着跳过当前步骤时，把后续步骤移出视野。反过来，把几个序列合并会让每一步都看到后面的步骤，容易过早结束。
- 按调用方式拆：见下文“调用方式”。

## 关键词

关键词是模型预训练中已有的紧凑概念（如“教训”“战争迷雾”“曳光弹”），代理执行时用它思考。反复使用同一个词，它会积累出完整含义，用最少的 token 锚定一片行为，而且同一个词出现在提示、文档和代码中时，代理更容易把它们联系起来并找到对应材料。

- 寻找可以收拢成一个词的重复表述：三处都写“快速、确定、低开销”可以改成“紧凑的”反馈环；“一个你信得过的反馈环”可以改成“能变红”的反馈环，把模糊门槛变成可观察的二元状态。
- 自造词只要定义清楚也能用，但不会调用任何先验知识，优先用已有的词。

否定会适得其反：“不要想大象”反而让大象更显眼，禁令常被读成要做的事。写出期望的正面行为，让被禁止的行为不被提起；只有无法正面表达的硬性护栏才保留禁令，并且同时写出应该怎么做。

## 精简

- 每个意思只在一个地方权威地写一次，修改行为只需改一处。重复会增加维护成本和 token，并让这条内容显得比实际更重要。
- 环境本身就是事实来源（`package.json` 脚本、配置文件、目录结构、`--help` 输出）。文档复述它们就是一份缓存，只有查询代价高时才值得。只写代理查不到的东西：未成文的约定、选择背后的原因、配置里看不出的坑。
- 逐行检查相关性：是否还和文档要做的事有关。只加不删的文档会沉积过期内容。
- 逐句做无效检查：模型默认就会做的指令只是付出负担而什么都没说。测试标准是“与默认行为相比是否改变了行为”，这取决于模型而不是读者；有分歧时运行文档验证，不靠争论。不通过的句子整句删除，不只删几个词。太弱的关键词（代理本来就比较细致时写“要细致”）也是无效的，换成更强的词（“穷尽”），而不是换一种写法。

## 调用方式

- 模型可调用的技能保留 `description`，代理可以自行触发，其他技能也能调用它；用户仍可手动输入名字调用。代价是描述常驻上下文。只有内容为参考的模型可调用技能，也可以作为多个技能共享参考的存放处。
- 只允许用户调用的技能（如设置 `disable-model-invocation: true`）不占上下文，但需要人记住它存在，其他技能也无法调用它，描述变成给人看的一行摘要。只在手动触发的技能用这种方式。
- 只有存在一个会在提示中独立出现、应单独触发的关键词，或其他技能必须调用它时，才拆出新的模型可调用技能。
- 只允许用户调用的技能多到记不住时，用一个只允许用户调用的路由技能列出它们和各自的使用场景；它只能提示，不能替人触发。两个只允许用户调用的技能都需要的共享参考，放在技能体系之外的普通文件里。
