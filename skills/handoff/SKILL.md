# 任务交接

## 目标

把当前工作整理成下一位代理或下一轮对话能直接接手的状态。
重点保留事实、路径、命令结果、未完成项和风险，不复制完整聊天记录。

## 何时使用

- 用户要求整理当前进展或生成交接说明
- 长任务已经跨多个阶段，后续需要继续执行
- 上下文即将压缩，需要避免丢失关键事实
- 需要把当前线程的结果交给另一个线程、代理或人工继续

## 何时不要使用

- 任务很短，最终回复已经足够说明状态
- 用户只是要提交、推送、PR 文案或代码评审
- 交接内容会泄露密钥、令牌、私钥或敏感配置值

## 交接内容

按需包含这些部分：

- `目标`：用户原始目标和当前目标是否发生变化
- `当前状态`：已经完成什么，哪些文件/仓库/分支受影响
- `决策`：已经做出的关键判断，特别是用户明确拍板的范围边界
- `证据`：重要命令、测试、日志、链接或输出结论；只写结论和可复跑命令
- `未清理状态`：未提交改动、未推送提交、运行中的服务或临时文件
- `持久文件`：若存在 `task_plan.md`、`findings.md`、`progress.md`、PRD、问题或设计文档，列出路径和当前权威来源
- `剩余工作`：下一步最小可执行动作
- `风险`：未验证、需要用户确认、可能过期或依赖外部状态的内容
- `建议技能`：下一轮最可能需要用到的技能，例如 `systematic-debugging`、`requesting-code-review`、`git-commit`

## 委托给其他代理或协作者

当实现、审查或修复需要交给另一个代理、线程或人工时，额外写一份可冷启动的委托说明。不要只写“继续之前的工作”；接手者必须能根据路径、决策和验证命令独立开始。

至少包含：

- `角色`：`implement`、`review` 或 `fix`
- `目标与约束`：本次要完成什么，以及会影响接手工作的限制
- `当前状态`：分支、工作区状态、已修改文件和已知失败
- `决策与约束`：已经确定的方案、兼容性要求和禁止的副作用
- `场景契约`：`test-scenarios.md` 路径；没有时明确写 `none`
- `验证入口`：允许执行的命令、应观察的结果和不需要运行的重型检查
- `返回契约`：要求返回改动摘要、场景覆盖、验证结果、剩余风险和未完成项

审查委托默认只读；修复委托只处理已确认的问题。不要让审查者直接修改源文件，也不要把未确认的建议扩大成修复范围。

## 写法要求

- 用短句和具体路径，不写泛泛总结
- 明确区分事实、推断和待确认事项
- 保留能继续执行的命令，但不要堆完整日志
- 不重复已经存在的 PR 正文、计划文档或变更日志，只引用路径或链接
- 不写“已经完成”除非有当前验证证据

## 安全约束

- 不复制令牌、私钥、会话 Cookie、一次性验证码、内部密码
- 如果命令输出包含敏感值，只写“已确认存在/缺失/匹配”，不要贴原值
- 对可能过期的外部状态标注检查时间或说明需要重新验证

## 输出模板

```text
## 交接

目标:
- ...

当前状态:
- ...

决策:
- ...

证据:
- ...

未清理状态:
- ...

持久文件:
- ...

剩余工作:
- ...

风险:
- ...

建议技能:
- ...
```

如果存在委托动作，在上述内容后追加：

```text
## 委托说明

角色: implement / review / fix
目标与约束:
- ...

当前状态:
- ...

决策与约束:
- ...

场景契约: <path / none>
验证入口:
- <command>: <expected result>

返回契约:
- <summary / coverage / validation / risks>
```
