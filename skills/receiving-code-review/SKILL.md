# 处理代码审查意见

开始时声明："我正在使用 receiving-code-review 技能分析并处理评审意见。"

## 目标

收到评审意见后，不机械照改，而是先理解、验证、判断，再决定是否修改代码。

## 核心原则

- 先验证，再修改
- 不为了“显得配合”而盲目同意
- 以代码事实、测试结果、项目约定为准
- 不清楚的意见先澄清，不能靠猜

## 何时使用

- 用户贴了评审者评论，让你处理
- 用户说“根据评审改一下”
- 某条评审意见看起来不一定对
- 多条评审意见之间可能冲突

## 何时不要使用

- 用户只是要你主动做一次代码审查
- 用户只是要你创建 PR
- 当前并没有明确的评审意见输入

## 处理流程

1. 完整读取评审意见，不急着承诺修改。
2. 用自己的话复述每条意见要解决的技术问题。
3. 对照代码、测试、项目约定验证该意见是否成立。
4. 判断是：
   - 直接修改
   - 需要澄清
   - 应该技术性反驳
5. 按优先级逐条处理，并验证每项修改没有引入回归。

## 代码检查维度

在判断评审者意见是否成立时，至少从这些维度检查：

- 正确性：是否会引入缺陷、panic、边界条件错误
- 回归风险：是否破坏现有行为、兼容性或已有调用方
- 测试覆盖：当前意见是否需要补测试，已有测试是否能证明对错
- 可维护性：是否让代码更清晰，还是只是换一种写法
- 性能：是否引入明显不必要的性能损耗
- 安全性：是否带来权限、注入、敏感信息泄露等风险
- 项目约定：是否符合仓库已有模式、命名、目录结构、接口习惯

## 对不清晰意见的处理

如果有任何一条意见理解不完整：

- 先停下，不要部分实现
- 明确指出哪几条已理解，哪几条需要澄清
- 不要假设评审者想表达的真实意图

## 何时可以反驳

以下情况应该明确技术性反驳，而不是照改：

- 建议会破坏现有功能
- 评审者缺少上下文
- 建议和项目既有约定冲突
- 建议属于过度设计，当前没有真实需求
- 建议在当前技术栈或版本下不成立

反驳方式：

- 给出代码、测试、行为或兼容性依据
- 只讲技术事实，不做情绪表达
- 若涉及架构取舍，明确交由用户决策

## 建议输出方式

对每条评审意见，输出其中一种结果：

- 已确认成立，准备修改
- 已修改，并说明改动点
- 需要澄清，并指出不清楚的部分
- 不建议采纳，并给出技术理由

## 输出模板

```text
评审意见： <原意见摘要>
决策：接受 / 已修改 / 需澄清 / 不采纳
原因： <技术原因>
证据： <代码、测试、行为、约定中的证据>
```

## 关键约束

- 不要先说“你说得对”再去验证
- 不要批量照改单条评审，应该逐条确认
- 不要对无法验证的意见假装确定
- 不要为了迎合评审者牺牲正确性
